## 1. Import and export

Modules go out to a folder as `.bas` and `.cls` and come back from one, the same files the
companion editor writes, so a repository can be worked on from either end. A toolbar button opens
one card with the direction on it.

**The dialog and the api cannot disagree, by construction.** Both reach `HandleSync` in the shim.
The dialog draws the plan and posts back the rows that are ticked; it does not know how to write a
file. `tools/harness/module-sync.mjs` proves it by applying the same import each way and comparing
the result byte for byte, and it runs in the gate.

**Two planners, switchable in Settings, sharing one apply.** The default runs xlide_vscode's own
`moduleSyncPlan.ts` inside the engine, imported from that checkout the way the analyzer already is,
so both products decide file names, module kinds and staleness identically. The built-in one is
C# in `Xlide.Vbe.Core.Sync` and needs no engine. The gate runs all 32 checks through each.

**The plan says which planner made it** (`plan.planner`). That field exists because the fallback to
the built-in planner is silent by design, and a suite that cannot tell them apart tests whichever
one answered. Mine did exactly that: 31 green checks against the built-in planner while asking for
the shared one.

**Encoding is the trap.** The editor's `Export` writes in the machine's ANSI code page and this
product writes UTF-8, so the source is assembled rather than copied: the header comes from a
temporary export read as Latin-1, the body comes from the code module over COM as UTF-16. Import
runs it backwards, importing a header-only file and writing the body through COM. Nothing
non-ASCII ever passes through a file handed to the editor.

Documented in `docs/driving-excel.md` section 3b, with a runnable example.

## Defects worth remembering

**Zero errors and nothing checking looked identical.** The engine runs in its own process and is
not restarted if it dies. Everything else kept working and the Problems panel kept reading
`0 Errors`, which is what it reads about code that is genuinely clean. It says so now, once, at the
moment a pass is wanted and cannot run, which is the honest moment because something just changed
and nothing analysed it. A timer was the obvious hook and never fired: a settled editor stops
polling altogether.

**Every error was an identifier, not a sentence.** `UseSystemResourceKeys` strips the framework's
message text, so a locked file surfaced in the dialog as `IO_SharingViolation_File`. Measured before
changing it: the words cost 23,040 bytes, 0.3% of the library. The installer project still sets the
flag and is untouched, different audience, unmeasured.

**The engine held every module a session ever analysed.** The analyzer keeps an incremental parse
per document and drops one on `module/didClose`, which this product has never sent, correctly,
because a tab closing is not a module leaving. Closing the workbook did not release it either.
Released on project close now.

**Excel froze for 2.2 seconds to work out a plan.** The dialog's handler runs on the host UI thread
and the shared planner waited on the engine from inside it. The COM read stays on that thread
because the object model is apartment bound; nothing after it does. Proven by polling the host
while a plan ran: 4,689 answers, longest gap 18ms.

**A plan was 15.1MB**, 100% comparison lines, for a dialog that shows one row at a time.
Condensed and capped to 0.31MB, and 3.5KB for a project in sync.

**The module list could not be used without a mouse**, while announcing itself as a listbox.

## Four gate checks were lying, and that is the theme

Every one of them cost real time before it was understood, and three of them made me suspect the
product first.

| check | what it did | what it was |
| --- | --- | --- |
| `caret lands inside the procedure` | passed, then three later checks failed | it asserted the command RAN, not that the caret LANDED. Run then opened the Macros dialog and nothing reached a breakpoint |
| `the editor keeps the room the sections do not claim` | failed on every fresh session, passed on a warmed one | the fixture seeded 260 + 300 pixels of docks into a 640-wide window. The check was RIGHT |
| `the sweep gives back the handles it takes` | failed twice on a clean build | one row jumped 350 while every other sat at zero. A leak of one per request cannot hide in one row |
| `the host did not grow unreasonably` | passed alone, failed in the gate | it counted kernel handles, which the door's own HTTP sockets dominate. It was measuring the harness |

The pattern: **a verdict is not a diagnosis.** Three of those survived a stash, a revert to the
previous commit, and a layout reset without moving, because none of those was the cause. What
found them each time was printing the numbers the check was judging.

If a probe fails, capture the state AT THE MOMENT OF FAILURE before believing anything about the
product.

## Where the time actually goes

Measured on `PerfFixture.xlsm`, 7 modules, 81,795 lines.

| | |
| --- | --- |
| read the modules from the editor | 55ms, COM, cannot leave the host thread |
| read the folder | 19ms for 7 files, now parallel |
| work out the plan, built in | 201ms, comparisons parallel and skipped when a row already agrees |
| work out the plan, shared | 1,616ms: 888ms in the engine, 749ms getting there and back |
| typing, p95 | 8.3ms |
| tab switch, median | 12.1ms |
| startup to a usable surface | 497ms, engine connected at 82ms |

Each phase of a plan logs its own cost, so the next person does not have to build the instrument.

**Parallelism that was not worth it, with the numbers:** the export's file writes stay serial
because writing seven files of three megabytes took 222ms while the plan that wrote nothing took
460ms, and they are the part that changes a developer's files. Reading a module's attribute header
costs about 1ms per class module and a cache would want invalidating on anything that recreates a
module. The engine round trip is not ours to divide: the payload is every module's full source and
it has to be, because the copy the engine already holds has no attribute headers.

## Open, in the order I would take them

1. **A module at VBA's 65,534-line ceiling, edited.** Never tested. The write-back is a whole-module
   replace above a certain size, and what the editor does at the ceiling is unknown.
2. **Two Excel instances against one export folder.** Single-instance is serialised by the host
   thread. Cross-process is not, and xlide_vscode keeps a per-folder lock this side does not have.
   A locked file is already reported honestly, which is the failure that matters most.
3. **The analyzer's 2.4s rules walk** on a 64,802-line module. Upstream by standing rule; worth an
   issue on xlide_vscode.
4. **`docs/handoff.md` is a running log** and its older entries describe tools that have since been
   removed. That is honest history, but a reader coming to it cold cannot tell which parts are
   current.
