# Findings, 2026-08-07

One session's worth, kept separate from [lessons.md](lessons.md) because it is dated rather than
cumulative. The long-form list there is the reference; this is what a single day of parity work,
an adversarial bug hunt, and the first piece of the debugger actually cost.

Environment as in lessons.md. Everything below was established by running against a real host,
except where it says otherwise.

The most expensive class of mistake here was not in the product. It was **probes that tested
themselves**, and there are nine of them below. A measurement you have not checked the shape of is
a claim, not evidence.

Two of them are the reason `ui/editor/src/devsurface.ts` exists: the page now reports its own state
and performs its own actions, so a probe stops hand-rolling a `querySelectorAll` per question and
stops guessing which events a handler listens for.

## Measuring

### 1. A probe can read back its own previous answer

Monaco reuses an open hover widget: triggering `editor.action.showHover` at a position that already
has one re-shows what is there instead of asking the provider again. So a probe that only triggers
and reads the DOM returns the same string in every state, including states where the feature is
switched off.

The obvious repair made it worse. Reloading the page to get a fresh widget wipes the page-side
cache the feature depends on, so the value was legitimately absent and the feature looked broken.
Removing the widget node by hand breaks monaco's hover lifecycle, so nothing renders at all.

What settled it in one call was asking the underlying state directly, `bridge.localValue(...)`,
which returned the value while stopped and null after reset. Check the state, then check the
rendering, and only trust the rendering once you know what it should say.

### 2. `/eval` answers are encoded twice

The browser returns a script result as JSON, and the door carries that as a JSON field, so a script
that builds its answer with `JSON.stringify` comes back quoted twice. One parse leaves a **string**
that reads as an object right up until every property of it is `undefined`, and a probe then
reports `false` for something that works. This happened twice in one day before the reply grew a
decoded `value` field.

### 3. A fixed sleep is a race that has not lost yet

`settle(2500)` was correct until a host round trip joined the path it was waiting on, and then it
reported a working feature broken. The door has an `await` route that polls a predicate inside the
page and answers how long it took; the client exposes it as `until`. Wait for the condition, not
for a duration.

### 4. The heartbeat cannot detect a modal

A VBA modal PUMPS messages, so marshalled work still runs and the host thread keeps completing poll
ticks the entire time it is blocked. Measured: under 140ms throughout fourteen seconds of being
stuck behind a compile error. What is standing is the only evidence that something is standing.

### 5. A fixture built through the api still needs saving

The twin workbook's modules were added through the door and never saved, so restarting Excel
emptied it. The next navigation failed with "no pane", which read as a broken fix to the navigation
code that had just been changed. Two rounds went into the wrong file.

### 6. An experiment run in a contaminated project answers a different question

"Does a procedure of the same name shadow a module for a qualified call?" was first asked inside the
rename fixture, which **deliberately does not compile**: `Helpers` and `Rival` both declare a public
`Recalculate`. Every `Run` against it fails for a reason of its own, so both halves of the
experiment failed and the conclusion would have been wrong. Redone in a workbook of its own, the
answer was clear and the opposite in one case.

Corollary: never compile the rename fixture as part of a wider experiment.

### 7. A measurement inside a request cannot see anything the request is blocking

A `trip caret` route set the host's caret and polled the page until it agreed where it landed. It
reported that the caret never moved, through four seconds a sample, five samples running. The same
sequence driven from OUTSIDE landed on the first poll, in about 50ms.

A route body runs **on the host thread**. `SetCaret` posts a web message, and a posted message is
delivered by that same thread's pump, so the post could not be delivered until the body returned,
and the body would not return until it saw the post. `Thread.Sleep` between polls changed nothing:
it yields the CPU and pumps nothing.

`RunPageScript` survives this because `ExecuteScript`'s answer comes back by a path the blocked
thread still completes. `PostWebMessageAsString` does not. So: **anything that observes a POSTED
effect has to be measured across requests, on the client side of the door.** That binds every
future route, not the one it was found in.

### 8. An argument that crossed a query string is a string

`act("expandWorkbook", { open: false })` expanded the workbook. Arguments ride the door as query
values, so `false` arrived as `"false"`, and `Boolean("false")` is `true`. Expand and collapse were
one action for as long as it took to notice, which was one call, because the reply said "expanded"
and the tree agreed with the reply.

Cheap to fix and cheap to miss: the coercion belongs in one helper at the boundary, not written out
per argument at each use.

### 9. An instrument that reports nothing has to be shown reporting something first

Three of the instruments built today were wrong in ways that read as good news.

The long-task observer reported no jank. Provoking a 200ms stall through the `eval` route still
reported no jank, which is what a broken observer looks like. It was not broken: **a stall
provoked from a debug-api script is not a page task and no observer sees it.** Provoked from a
`setTimeout` inside the page, the same observer caught it immediately. Had the first zero been
believed, "the surface has no jank" would have been the conclusion.

The `hostcall` trip reported 0.001ms to reach the host thread. `RunOnHostThread` enqueues and sets
a timer rather than waiting, so it was timing an enqueue and calling it a round trip. Deleted: a
route body is already ON the host thread, so the question is unanswerable from there, and
`perf().marshalMs` has measured it from the correct side all along.

The `act` route reported `did: true, closed Watcher` five times over a tab that never moved, with
a Save / Don't Save / Cancel box standing on screen the whole time — and `ui.dialogs` reported no
dialogs, because its list of dialog ids did not include the close-confirm. Two instruments wrong
at once, each hiding the other.

Every one of them was caught by asking the instrument to report a thing that was definitely there.

### 10. The dialog list should have been a question, not a list

`ui.dialogs` was a hand-kept map of element ids and it was incomplete on the day it shipped. It
missed the one dialog most likely to be up when something looks stuck.

Every dialog the page builds already sets `aria-modal="true"`, because that is what makes it a
dialog to a screen reader. Asking the DOM for that reports a dialog added next year with nothing
to remember. Where a list and a question give the same answer, the question stays right.

### 11. Language is not one exposure, and the companion's tests do not cover this one

xlide_vscode reads and writes the workbook's VBA streams itself, so its language risk is decoding
bytes against `PROJECTCODEPAGE`, and its matrix is built around patching that record. This product
never touches those bytes: text arrives as a COM BSTR, already UTF-16. Its risk is **offset
arithmetic** — every language feature names a position as a number of units into the source, and a
byte or code-point count anywhere in the chain drifts by the width of the non-ASCII text to its
left. Invisible in English, worse further down a file, and it corrupts an edit rather than failing
one. 18 scripts and astral emoji now run through open, diagnose, outline, definition and rename as
a gate step, and pass.

The other half is not ours and cannot be made ours: **VBA stores module text in the system ANSI
code page.** On this machine, accented Latin survives a write and Cyrillic, Greek, Hebrew, Arabic,
Thai, CJK and emoji come back as question marks — from Excel, before xlide sees them. That the
companion has to patch `PROJECTCODEPAGE` to test other languages is the same fact from the other
side.

### 12. A door that cannot reach a state is why that state's defects are found by hand

Three defects in this codebase have the shape "a name is not an identity across workbooks", and
all three were found by a person noticing something on screen. The reason turned out to be that
the two-workbook state was **unreachable from a script**, for two separate reasons in the door
itself:

- the `project` route reported its `projectId` from `_shownProject`, so asking about the second
  workbook returned that workbook's components under the FIRST workbook's id. The reply
  contradicted itself, and a caller doing the obvious thing — read `projectId`, pass it to the
  next route — was then addressing the wrong workbook while holding a reply that looked right.
- `pane open` computed the owning project and never passed it on, so `project=` did nothing and
  a bare name always resolved shown-project-first.

With both fixed, a randomised walk found a FOURTH member of the family within twenty steps: the
explorer treated a null `expandedModuleWorkbook` as "every workbook", so unfolding `Helpers`
unfolded both workbooks' copies at once. An accordion that opens two rows is not an accordion.

`Start-Excel.ps1` takes a list of workbooks now. The harness could not set up the state that
three defects lived in, which is a harness defect, not luck.

### 13. A clean run has to say which states it reached

The first randomised walk reported 1,223 checks and nothing broken. It had spent 54 of its 70
steps with an empty workspace, had never split, and had never once held two modules of the same
name — every check about those passed because the state never happened. It would have reported
exactly the same clean run with the checks deleted.

Two changes made it mean something. The actions are weighted, because unweighted there are two
ways to close a tab and one to open one, so the walk drains to empty and stays. And it prints the
states it reached, with the ones it never reached called out as vacuous. Only after that line
appeared did the walk start finding things.

### 14. A feature with no api coverage has never been exercised by anything but a hand

Find/replace and bookmarks had no route, no snapshot field, and no way to drive them. Adding that
coverage — a standing requirement now, alongside the feature rather than after it — found two
defects inside an hour, and both were in the coverage itself, which is the point: the code that
drives a feature is the first thing to exercise it.

`act("bookmark", {do: "toggle"})` became `do=bookmark&do=toggle`, because `do` is the route's own
action selector and the argument overwrote it. The door answered "unknown action toggle" and four
bookmark checks failed for a reason with nothing to do with bookmarks. The argument is `which`
now, and the CLIENT refuses a `do` argument outright rather than building a request that cannot
work.

And the search widget's `find` accepted `matchCase` and applied nothing, so a case-sensitive
search for `recalculate` still found `Recalculate`. The toggles are pressed through their buttons
now, because pressing them is what runs the handler that re-searches; setting the attribute alone
leaves the widget showing one thing and searching by another.

Neither feature was broken. Both were unobserved.

### 15. A refusal can be a null rather than an exception

With "Trust access to the VBA project object model" off, `$excel.VBE` and `Workbook.VBProject`
evaluate to **nothing** through PowerShell's COM binder. They do not throw. A probe written as
`try { ... } catch { }` reports success and prints an empty string, so the first run of that
experiment said the gate was open when it was shut. Test it as `$null -eq $excel.VBE`.

## Design

### 16. A provider that acts is answering a question by acting on it

`provideDefinition` navigated through the host when the target was in another module. Every command
that asks where something is declared comes through that one provider and it cannot tell which is
asking, so Peek asked and was taken there.

It could not have reported the answer either. The editor wraps a symbol navigation request in an
`EditorStateCancellationTokenSource(editor, Value | Position)`, so moving the caret while a provider
runs **cancels the request that asked**. The jump and the silence were one act. Providers answer;
`registerEditorOpener` acts.

Two things about that opener, neither known when it was first attempted: handlers are stored with
`unshift` so the last registered runs first, and the wrapper requires the opener to resolve `true`.
Anything else reads as "not handled" and falls through to the built-in one, which only ever opens
the model already attached to the asking editor.

### 17. Two lists that must agree need one funnel

The tab strip and the explorer tree are separate publishes, and the analyzer is a third thing.
Nothing refreshes on its own, so every site that adds, removes or renames a component has to say so,
and each one remembered a different subset. Inserting a component from the page told the analyzer
and neither list; the first version of the `component` route told the strip only, leaving the
explorer describing a different project from the one the strip described.

One method now, and the question "did you remember to refresh the tree" has one answer.

### 18. A name is not an identity across workbooks

Two open workbooks can each hold a `Helpers`. Three tables in this codebase key on the module name
alone, and each is a defect of the same shape:

- **navigation** compared the shown module by name, so going to the other workbook's `Helpers` moved
  the native pane and left the surface where it was. Fixed.
- **the tab label** was right, but its render key was per group, so a twin opening in another group
  never redrew the tab already there. Fixed.
- **the explorer's accordion** read a null owning workbook as "every workbook", so unfolding a
  shared name unfolded both copies at once. Fixed 2026-08-07, and found by a randomised walk
  rather than by eye — the first of this family that was.
- **breakpoints** were keyed by name. Setting one in the twin reported against the other and a run
  that should have stopped did not. Fixed 2026-08-08: the record is keyed by workbook and module,
  the toggle finds the SHOWN project's pane rather than the first of that name, and the
  `breakpoints` route reports `project` alongside `module`.

  The fix had a second half worth naming. The key is lowercased, because VBA does not distinguish
  `Helpers` from `helpers`, and the first version reported the KEY back — so the route answered
  `helpers @ renamefixture.xlsm` and a caller comparing against the name on screen matched
  nothing. A door that mangles its own answers is worse than one that refuses. The spellings are
  kept beside the key now.

That is the whole known family, closed. It took a harness that could reach the state.

### 19. A write that fails must fail in its reply, not only in the log

`writeModule` answered the same way whether the module took the text or not; the refusal went to the
log. A fixture built on unchecked writes came out with an empty `Rival`, so the duplicate
`Recalculate` was not there, so it no longer exercised the one collision it exists for. It looked
fine.

The underlying cause is worth its own note: an **empty** module has `CountOfLines` 0, but an empty
baseline splits into one empty line, so the windowed write asked to delete a line that was not there
and the editor refused the whole write.

### 20. Read the result out of the object model, not out of the thing under test

A feature that reports its own success is reporting its intent. Reading the module back through the
VBA object model found two real defects on 2026-08-06 and the empty `Rival` on 2026-08-07. The api's
`readModule` and `project` routes do this from inside, so it costs nothing and needs no trust
setting.

### 21. An undo that spans documents cannot be the editor's undo

A rename edits every module that uses the symbol and an editor's undo stack is per model. Ctrl+Z in
the module on screen reverses that module's share and leaves the rest renamed, which is a
half renamed project from a keystroke that means "put it back". Worse than no undo at all.

What is kept for the reversal is the text read **out of** each module immediately before writing,
not the text the engine was handed: the editor rewrites what it is given.

### 22. A cached value from a frame that has gone is worse than no value

Data tips read the Locals panel's own snapshot. Leaving break mode has to drop it immediately rather
than waiting for a locals push to say so, because reset produced no such push and the hover went on
reporting a value that looked current and was not.

### 23. State that follows the editor has to follow it back to empty

Two defects on the way out of the last tab, both the same shape. Closing a tab fell back to whatever
the group listed first, which is not where anyone was: the fix is a stack of what has been shown,
popped on close. Then the tree kept a workbook unpacked with nothing open underneath it, because the
first version deliberately spared workbooks on the grounds that expanding one is a hand-made choice.
It is, but so is opening a tab, and the developer's answer was that with nothing open the tree should
read as at rest. Automatic state has a resting position, and reaching it is part of the feature, not
a separate one.

Resetting `expandedModule` was not enough on its own: `attentionWorkbook` had to go too, or reopening
in the SAME workbook would count as "the attention has not moved" and leave it shut.

## The platform

### 24. "Trust access to the VBA project object model" is not needed

Verified with the box unticked. `Workbook.VBProject` and `Application.VBE` both come back null,
`Application.Run` is not gated, and `CommandBars.ExecuteMso('VisualBasic')` opens the editor. The
add-in is a VBE add-in: the host hands it the `VBE` object at `OnConnection`, so it is already past
the gate, and it read modules, wrote them, and drove a compile throughout.

The whole harness now works with the setting off, including building a fixture, because components
are added through the door. That matters beyond convenience: requiring a security setting to be
lowered before a product works is an adoption barrier, and the setting exists to stop macros
rewriting each other.

### 25. The page and the shim have different development loops

The bundle is served over loopback from a folder on disk, read per request, so a page change needs a
copy and a reload. What forces a restart is the shim, because a host holds an add-in library open
for its lifetime. Doing the shim's loop for a page change costs about a minute each time, and this
session did it a dozen times before noticing.

### 26. `alternativeDefinitionCommand` only accepts a symbol navigation command

The editor looks the configured id up in `SymbolNavigationAction._allSymbolNavigationCommands` and
runs it as one of those. A plain command id is never found, so the fallback silently never fires
whatever it is pointed at. That is why Go to Definition on the declaration appeared to do nothing.

### 27. PowerShell 5.1 writes a BOM for `-Encoding utf8`

`JSON.parse` refuses one, naming a character that does not appear to be in the file. Use
`[System.IO.File]::WriteAllText($path, $json, (New-Object System.Text.UTF8Encoding $false))`.

## Process

### 28. A table is complete the day it is written and quietly is not, six entries later

Asked whether every route was documented, the honest answer needed a diff rather than a memory:
`debug-api.md` had all thirty two, `driving-excel.md` had twenty, and one route had no client method
at all. `tools\harness\audit-routes.mjs` reads the route cases out of the shim and fails when one is
missing from either document or unreachable from the client. It is a gate step, and it caught the
next new route before it landed.

### 29. A check whose answer depends on where you are standing is not a check

The gate's Release steps ran bare `dotnet build` and `dotnet test`, which pick the solution out of
the current directory. It passed from the repo root and failed with MSB1003 from anywhere else.

### 30. A style rule given twice needs weighting, not just recording

Em dashes are banned in prose and product strings by the standing style guide, and had already been
flagged once for the Object Browser. They were still reaching the tab strip, these documents, and
every reply. Being written down was not enough; the memory entry now says which surfaces it binds
and to check before finishing a turn.

## What this bought

Eight confirmed defects from the adversarial pass, all fixed and pinned by nine cases in the engine
smoke test. Two open items closed, one of which turned out to be a navigation defect wearing a
rename item's clothes. Two issues filed upstream rather than patched here, because the analyzer is
shared and a fix on one side only makes the two products disagree. The debugger's first feature, and
a harness that can reach break mode, read what is stopped, and put it back.
