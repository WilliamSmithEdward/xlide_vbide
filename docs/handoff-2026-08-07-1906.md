# Handoff, 2026-08-07, 19:06 local (UTC-07:00)

Written at the end of the session that gave the product a door it can be driven and observed
through, and then used that door to find what nobody could see. The standing handoff is
[handoff.md](handoff.md); this one is a point-in-time record.

Head is `b45d003`. Twenty-two commits from `52f4c08`. Dev build: page **150**, 45 routes.

The session's arc: it began as a bug hunt, and turned into building the instruments that make
bug hunting possible. Nine of the defects below were found by an instrument built the same day,
and four of those were in the instrument itself.

---

## 1. The three standing rules this session established

These came from the developer during the work and are now in memory. They govern how the next
session should build.

**Build the api alongside the feature.** Every feature ships with the routes to drive and observe
it, documented in both api documents, in the same change. *Because:* three defects of the form
"a name is not an identity across workbooks" had all been found by eye, and the reason turned out
to be that the door could not reach the two-workbook state at all. Adding the reach found a
fourth within twenty steps.

**The api mirrors the UI.** An action through the api must leave, and report, the state the same
action through the UI would. A deviation is allowed but must be *designated* and heavily
documented where it is offered. *Because:* `act("hover")` called the bridge underneath the
providers, skipping the refusal every provider opens with, and reported hover healthy through an
entire session in which hover was dead on screen.

**Native parity is the definition of done, and it means CONTENT.** A feature touching the editor
is not fully tested until it validates parity with the native VBE panes underneath, and parity
means the code matches, not the names. *Because:* the surface held an empty document for a module
the workbook had 42 lines of. Every name comparison passed. The editor showed a blank page.

## 3. The performance work

The headline: **every hop to the host thread was waiting for a Windows timer tick.**

Work marshalled to the host thread rode `SetTimer(handle, id, 0, 0)`, and a zero-elapse timer does
not fire immediately: Windows clamps it to the system timer resolution, 15.6ms. The shim's own
marshal counter had been saying so all along: median 16ms, samples at 31 and 47, which are one,
two and three ticks.

The timer was chosen deliberately and the reason was recorded: posted app-range messages had never
been seen to arrive at this window. So it stays as the guarantee, and a posted message now goes out
beside it. It arrives. The marshal counter records nothing now, because it only samples non-zero
durations.

| | before | after |
| --- | --- | --- |
| `pagecall` floor | 15.5ms | **0.37ms** |
| promise floor | 47ms | **15ms** |
| hover, 109 lines | 15.6ms | **0.8ms** |
| hover, 11,252 lines | 31.3ms | **15.3ms** |
| completions, 11,252 lines | 30.9ms | **1.4ms** |

With the ticks gone the scaling curve shows its real shape: hover and definition track the
analyzer's share almost exactly, completions stay flat. **The feature cost is the analyzer's
cost.** The analyzer scales sub-linearly, 1ms to 13ms across 103× the lines.

Also: the door's promise polling backed off from a flat 40ms to 2ms doubling, and `EngineCounters`
now reports the analyzer's cost per method split into queued and on-the-pipe.

> **A correction I owe the record.** Mid-session I reported that completions spend more time queued
> behind diagnostics than working. That came from one sample taken while a large module's initial
> seeding was in flight and **does not reproduce**: under deliberate provocation the pipe shows 0ms
> queued against 110ms working. The one-at-a-time pipe is not a bottleneck in practice.

## 7. Added after this handoff: the Format Module squiggle, root-caused

The open bug at the top of this document turned out to be **two** defects with one symptom, and
both are fixed and verified end to end. Neither needed a guess: the first was settled by
arithmetic before Excel was restarted, the second by the parity check this document argues for.

### 7a. A finding measured in one text and drawn in another

A finding crosses from the engine as a character offset, and an offset means nothing without the
text it was counted in. `textDocument/diagnostics` may leave the source out, and then the engine
picks between its own live copy of the module and the copy the project was seeded with. That
choice was invisible to the add-in, which converted the offsets against the text it had last read
out of the editor.

Formatting is what drove the two apart. The page holds the formatted text the moment the format
runs; the editor underneath still holds the original until the write-back. A statement at indent 0
gains an indent, every character on the line moves along, and the finding lands columns away from
the word it is about, permanently, because nothing about waiting makes two different texts the
same.

The measured case, and the arithmetic that predicted it exactly before any host was involved:

| | the word | the finding |
| --- | --- | --- |
| before the format | 6:11 | 6:11 |
| after, as it was | 6:12 | **6:6** |
| after, now | 6:12 | 6:12 |

`6:6` is offset 74 read against the pre-format line index; `6:12` is the same offset read against
the text the engine actually analysed.

**The fix is that the engine sends the position it measured**, in the text it chose, alongside the
offset. Converting where the text is is the only place that cannot be wrong. The add-in keeps its
own arithmetic as a fallback for an engine too old to send one.

### 7b. A one-line format read as a keystroke

With the fix above in, the same run failed differently: the finding was right and the underline was
gone. A line being typed is not squiggled until the caret leaves it, and the host arms that hold
when a change touches exactly one line and inserts no newline, which is what a keystroke looks
like. Formatting a module whose lines are already right except one produces exactly that shape.

That is why the bug looked settings-dependent. With `format.useTabs` on, four lines change and no
hold is armed. With it off, only the offending line changes, the hold is armed, and the squiggle
disappears until the caret is moved off the line.

The editor's change event carries no source, so **the formatter now marks its own edits** and the
host stops reading them as typing.

### 7c. VBA will not store a tab, so the setting is gone

Found while asserting parity:

> **VBA's code store cannot hold a tab character.** The editor expands every one to the next
> four-column stop, on both write paths this product uses and mid-line as well as leading.

So **Format: indent with tabs** could never be reflected in the module: the page showed tabs, the
workbook held spaces, and the two disagreed for as long as a module stayed open, which is the one
thing a surface covering the host's own editor must never do. **The setting was removed** on the
developer's call the same day. Indentation is spaces, at the width **Indent size** still chooses,
everywhere: typing, smart Enter, Backspace and Format Module. A `format.useTabs` in an older
settings file is ignored rather than read.

What makes that bearable is Backspace. With `useTabStops` on, pressing it in a line's **leading
whitespace** takes back a whole indent level rather than one space; anywhere else it deletes one
character as it always has. `act("backspace", {times})` drives it, because the `type` route
cannot: that goes through `trigger("keyboard", "type")`, which only ever inserts.

Measured after the change, on the live editor: typing indents one level in spaces, smart Enter
after `If ... Then` indents another, no tab reaches the page, Backspace at the end of an indent
takes all four spaces at once, Backspace with code before it takes one character, and the native
pane agrees with the page throughout.
