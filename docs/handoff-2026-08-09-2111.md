## The theme: a report of success and a different outcome

Half the commits are one defect wearing different clothes. Something failed, the product said it
had worked, and the only trace was a log line. In order of what it costs a developer:

**A refused write cost the module its previous text.** A whole-module replace is two calls, delete
then add, and the editor can refuse the second. 2,002 working lines, asked to take a body the
editor would not have, came back as 31,956 lines of it. Neither body. The route replied ok. That
one fix reached every caller that had a failure path and never got there: rename and undo stop
where they stopped instead of reporting modules they never wrote, import counts a refused row as
failed, discard says when the saved text could not be put back.

**A line past 1,022 characters was written in half.** The editor breaks it rather than refusing it,
with no continuation, so a string literal is left unterminated. Refused now, naming the line.

**An import destroyed a repository file.** A file carrying characters outside the machine's code
page imported as question marks; the module then differed from the file and the next export
overwrote it. `1 changed, 0 failed` at both ends.

**An import destroyed unsaved typing.** Same path, worse: the developer is looking at the text when
it goes. Closing a tab in that state raises a save/discard/cancel gate; import took the edits with
no question.

**Three controls that did nothing.** The export delete dropdown never reached the plan, because the
control rebuilt itself and discarded the selection four lines before it was read. The Attributes
toggle had nothing to switch between for a `.cls` (upstream `#14`). The canonical-keywords setting
governed the only one of three canonicalisers that never got to act, and was removed.

**`Helpers.Recalculate` was the wrong colour**, spotted on screen. The member rule did not consult
`@projectProcedures` while both its neighbours did, so one procedure was painted two ways depending
on parentheses, and a VBA Sub takes its arguments without them.

**The host's ceiling is not the line count.** 65,000 lines of procedures are accepted; 65,000
module-level constants are refused at 32,446, on the identifier budget, and that leaves the whole
VBE unable to add a component until Excel restarts.

**Multi-language, precisely.** Everything this product does with text is multi-language and tested
as such. What a workbook can STORE is the system ANSI code page and no code here can widen it. So:
*xlide supports whatever the running VBA project's code page supports, and handles it correctly end
to end.* The case that hides is not a question mark: on code page 1252 `"cafe" + U+0301` becomes
`"cafe" + U+00B4`, a different real character, while the precomposed spelling survives. A
repository authored on macOS is decomposed.

## Four ASCII-only patterns, all ours

`Calculér` or `Вычислить` could not be navigated to, renamed, found by whole-word search, or
renamed TO.

```
ui/editor/src/vba.ts        Monaco's wordPattern, which getWordAtPosition uses
engine/src/navigation.ts    isIdentifierChar, used by identifierAt and six boundary checks
engine/src/navigation.ts    the rename validity check, which refused a non-ASCII NEW name
engine/src/search.ts        whole-word search
```

**I read this as an analyzer defect and said so twice, and it was never that.** The control was on
screen the whole time: the outline showed `Calculér` correctly, so lexer, parser and symbol tree
were fine, and an ASCII name in the *same module* resolved on the *same request*. Two issues WERE
filed upstream and both were fixed the same day: `xlide_vscode#12` and `#14`.

**`act("press", {key})` and `act("insert", {text})` are why several exist.** `type` inserts a
string through the HOST's pipeline, and Monaco applies enter rules only to a newline typed as one
character, so everything hanging off Enter was live-untested; and the host normalises what it takes,
so nothing could hand the page a keyword spelled non-canonically. `press` is not `key`, which
dispatches a synthetic event at the document for this product's own chords.

## Read this before trusting a red check

**My probes were wrong more often than the product was.** Each cost more than the defect it chased:

- reading `.line` where the page answers Monaco's `range.startLineNumber`
- no wait for the engine to seed a just-created module, which answers `0 definition(s)` in exactly
  the words a real failure uses
- passing a detail string to `check(name, got, want)`, whose third argument is the expected value
- `"NoticeNNNNProbe".includes("NoticeNNNN")` counting the probe's own scratch module
- reading the blank spacer line comfy block layout inserts, and calling a working indent broken
- comparing a *field* name to a *type* name, sampling only the first character
- pressing Enter on a Sub that already had its `End Sub`, where smart Enter has no block to build
- two attempts to wait out a precondition that was never going to arrive
- verifying a dialog after `Update-Page.ps1 -NoBuild`, which copies the bundle without rebuilding

**When a check goes red here, suspect the instrument first.** What found the truth every time was
printing the numbers the check was judging.

Two correct behaviours that will trip the next person:

- **The editor unifies identifier case.** `item` comes back `Item`. Assert case-insensitively.
- **`api.type`, `act("insert")` and `act("press")` are three different input paths.** Mixing them
  in one measurement puts the caret somewhere other than where you typed.

## Open, in the order I would take them

1. **The gate's `engine executable is current` step** compares against a checkout that moves. It
   fired on four runs where nothing was wrong, and once meant measurements ran against an engine
   older than the analyzer under test. Make packaging the gate's first action rather than something
   it asserts afterwards.
2. **Two Excel instances against one export folder.** Files are written atomically now, so nothing
   reads a half-written module, but there is no per-folder lock as xlide_vscode has.
3. **The insert menu**, requested during this session: one toolbar button replacing the native
   Insert menu, a flyout listing every open workbook, hovering one revealing Module / Class Module
   / UserForm. `component add` already takes `kind` and `project`, and `projects` lists every open
   workbook, so the api half exists. Settle first what happens with one workbook open, where a
   flyout to choose a workbook is friction with only one answer.
4. **`EditorSurface.OnMessage` is 651 lines over 36 cases.** Measured and deliberately left: no
   pre-existing seam, each case short, moving one method to a partial would be churn for a metric.
