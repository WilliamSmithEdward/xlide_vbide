## The theme: a report of success and a different outcome

Nine of the sixteen commits are the same defect wearing different clothes. Something failed, the
product said it had worked, and the only trace was a log line. In order of what it cost:

**A refused write cost the module its previous text.** A whole-module replace is two calls, delete
then add, and the editor can refuse the second. A module of 2,002 working lines, asked to take a
body the editor would not have, came back holding 31,956 lines of it. Neither body. The route
replied ok. The writer keeps the old text in hand now and puts it back, and the complaint is
returned rather than swallowed. That one change reached every caller that had a failure path and
never got there: rename and undo stop where they stopped instead of reporting modules they never
wrote, import counts a refused row as failed, discard says when the saved text could not be
restored.

**A line past 1,022 characters was written in half.** The editor does not refuse a long line, it
breaks it, at 1,023, with no continuation: a 2,018-character `Debug.Print "aaa..."` became a
1,023-character fragment carrying an unterminated string. Refused rather than repaired, because a
continuation would have to go inside the developer's expression.

**An import destroyed a repository file.** VBA stores module text in the system ANSI code page, so
a file carrying Cyrillic imported as question marks, the module then differed from the file, and
the next export was ticked and overwrote it. One import and one export, byte for byte destroyed,
`1 changed, 0 failed` at both ends.

**An import destroyed unsaved typing.** Same path, worse: the developer is looking at the text when
it goes. Closing a tab in that state raises a save/discard/cancel gate; import took the edits with
no question and no notice.

**`Helpers.Recalculate` was the wrong colour**, spotted on screen by the developer. The member rule
did not consult `@projectProcedures` while both its neighbours did, so one procedure was painted
two ways depending on whether it had parentheses. A VBA Sub takes its arguments without them.

**Choosing "Delete them" on an export never reached the plan.** `refresh()` rebuilds the dropdown
and discards the selection four lines before reading it, so the plan was always asked for with the
keeping mode and the control snapped back on its own. The api was never affected, which is why
nothing caught it.

**The host's ceiling is not the line count.** 65,000 lines of procedures are accepted; 65,000
module-level constants are refused at 32,446, on the identifier budget, and that leaves the whole
VBE unable to add a component until Excel restarts. Removing the module does not give it back.

**Multi-language, precisely.** Everything this product does with text is multi-language and now
tested as such: offsets, files, identifiers, colouring. What the workbook can STORE is the system
ANSI code page and no code here can widen it. So: *xlide supports whatever the running VBA
project's code page supports, and handles it correctly end to end.*

The case that hides, and it is not a question mark: on code page 1252 `"cafe" + U+0301` becomes
`"cafe" + U+00B4`, a different real character that renders almost the same, while the precomposed
spelling of the identical word survives. A repository authored on macOS is decomposed.

## Four ASCII-only patterns, all ours

A procedure called `Calculér` or `Вычислить` could not be navigated to, renamed, found by
whole-word search, or renamed TO.

```
ui/editor/src/vba.ts        Monaco's wordPattern, which getWordAtPosition uses
engine/src/navigation.ts    isIdentifierChar, used by identifierAt and six boundary checks
engine/src/navigation.ts    the rename validity check, which refused a non-ASCII NEW name
engine/src/search.ts        whole-word search
```

**I read this as an analyzer defect and said so twice, and it was never that.** The control was on
screen the whole time: the outline showed `Calculér` correctly, so the lexer, parser and symbol
tree were fine, and an ASCII-named procedure in the *same module* resolved on the *same request*.
That narrows it to the code between the offset and the lookup, which is ours. I filed nothing
wrongly, but only because I checked before filing.

Two issues were filed upstream and both were fixed the same day: `xlide_vscode#12` (an unqualified
call to a name two modules export is reported clean, though VBA refuses to compile it) and `#14`
(hiding headers still showed the class preamble).

**`act("press", {key})` is why several of those exist.** `type` inserts a string, and Monaco applies

product's own chords; Monaco does not act on synthesised events, so neither can do the other's job.

## Read this before trusting a red check

**My probes were wrong more often than the product was.** Every one cost more than the defect it
was chasing:

- reading `.line` where the page answers Monaco's `range.startLineNumber`
- no wait for the engine to seed a just-created module, which answers `0 definition(s)` in exactly
  the words a real failure uses
- passing a detail string to `check(name, got, want)`, where the third argument is the expected value
- `"NoticeNNNNProbe".includes("NoticeNNNN")` counting the probe's own scratch module
- reading the blank spacer line comfy block layout inserts, and calling a working indent broken
- comparing a *field* name to a *type* name and sampling only the first character, which is exactly
  where an ASCII-only rule still succeeds
- two attempts to wait out a precondition that was never going to arrive

**When a check goes red here, suspect the instrument first.** The corollary held all day: what
found the truth every time was printing the numbers the check was judging.

Two behaviours that will trip the next person, both correct:

- **The editor unifies identifier case.** `item` comes back `Item`, in the opener and in the
  generated `Next`. Assert case-insensitively.
- **`api.type` and `act("press")` are different input paths.** `type` goes through the host's
  keyboard pipeline, `press` reaches the page's editor. Mixing them in one measurement puts the
  caret somewhere other than where you typed.

## Open, in the order I would take them

1. **Cut 0.4.2.** Five data-integrity fixes plus the non-ASCII identifier work, all gated, most
   proven against the defect rather than only against the fix. Someone on 0.4.1 today can lose a
   module's text, have a line silently cut in half, have a repo file overwritten, lose unsaved
   typing to an import, and cannot use the export delete option at all. Prove the installer carries
   the newest engine by timestamp and by hashing the asset, per the standing rule.
2. **The gate's `engine executable is current` step** compares against a checkout that moves. It
   fired on four runs today where nothing was wrong, and once it meant intermediate measurements
   ran against an engine older than the analyzer under test. Make packaging the gate's first action
   rather than something it asserts afterwards: the run is then current by construction.
3. **Two Excel instances against one export folder.** Files are written atomically now, so nothing
   reads a half-written module, but there is still no per-folder lock as xlide_vscode has.
4. **`EditorSurface.OnMessage` is 651 lines over 36 cases.** Measured and deliberately left: unlike
   the debug api there is no pre-existing seam, each case is short, and moving one method to a
   partial would be churn for a metric. Recorded so it is not re-litigated.
